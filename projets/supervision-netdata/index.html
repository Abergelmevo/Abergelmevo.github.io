Ma première supervision : Netdata sur une VM Debian

Les lenteurs se découvraient quand un utilisateur appelait : j'ai installé Netdata sur une VM Debian et rattaché les serveurs Windows à un tableau de bord commun, premier pas d'un parcours qui mène à un SOC.

Contexte
Production · PME, VM Debian 11 sur Hyper-V, 6 nœuds supervisés
Période
Décembre 2024
Mon rôle
Réalisé en alternance, de la VM au rattachement des serveurs
Outils
Netdata · Netdata Cloud · Debian 11 · Hyper-V · Windows Server

En bref

Le problème

Lenteurs et coupures se découvraient quand un utilisateur appelait. Diagnostiquer imposait de se connecter à chaque serveur, sans historique ni alerte.

Ce que j'ai fait

J'ai monté une VM Debian 11 avec Netdata, rattaché cinq serveurs Windows à un tableau de bord commun et testé les alertes par une montée en charge CPU.

Le résultat

Six nœuds sur une vue commune, 12,4 k métriques et 53 règles d'alerte : un historique et des alertes, là où il n'y avait rien.

Contexte

Des serveurs ralentissaient, le réseau coupait par moments, et l'équipe informatique l'apprenait quand un utilisateur appelait. Il fallait alors se connecter à chaque machine pour chercher la cause.

J'ai retenu Netdata : installation en une commande, graphiques à la seconde, et un agent Linux comme Windows, pour un parc qui mélangeait les deux.

Ce que j'ai fait

  1. Une VM Debian 11 sur Hyper-VCréée sur l'hyperviseur de l'entreprise, avec une adresse IP fixe : c'est elle qu'on ouvre dans le navigateur et qu'on autorise dans les pare-feu.
  2. Netdata par le script officielkickstart.sh installe l'agent et démarre le service ; systemctl status netdata le confirme, et le tableau de bord local répond sur le port 19999.
  3. Rattacher les serveurs WindowsInstalleur déposé sur un partage restreint ; chaque agent rejoint l'espace commun de Netdata Cloud par un jeton qui permet d'ajouter des machines : il ne doit pas circuler.
  4. Vérifier les alertesRègles à deux niveaux, avertissement et critique. Montée en charge CPU provoquée sur un serveur : l'alerte remonte, et le pic se retrouve dans l'historique.
Voir les détails techniques

VM créée à partir de l'image Debian avec micrologiciels ; adresse fixe obtenue en désactivant le DHCP dans /etc/network/interfaces.

Terminal · l'erreur de l'incident

$ sudo apt update && sudo apt upgrade -y
admin n'apparaît pas dans le fichier sudoers. Cet incident sera signalé.
$ usermod -aG sudo admin
bash: usermod : commande introuvable

Une commande suffisait, depuis root (su - ou le shell du mode recovery) : /usr/sbin/usermod -aG sudo admin. L'essai ci-dessus échouait pour deux raisons : il faut déjà être root pour modifier les groupes, et usermod est dans /usr/sbin, hors du chemin de recherche d'un utilisateur ordinaire.

L'incident

« n'apparaît pas dans le fichier sudoers »

Problème

Sur la VM neuve, la mise à jour des paquets est refusée : mon compte n'a pas les droits sudo, et sans eux impossible de me les donner.

Résolution

Redémarrage sur le menu GRUB, entrée recovery mode, shell root : mot de passe root redéfini, droits de mon compte rétablis, mise à jour passée.

Résultats

Au moment du relevé : 6 nœuds, dont un serveur Windows hors ligne ce jour-là, 12,4 k métriques, 53 règles d'alerte actives et un avertissement en cours. Pour la première fois, l'état des serveurs se lisait avant qu'un utilisateur se plaigne ; je n'ai pas mesuré ce gain.

Ce que j'améliorerais

  • Je protégerais dès l'installation le tableau de bord local, que Netdata ouvre sans mot de passe : reverse proxy HTTPS avec authentification, ou accès limité à l'adresse locale.
  • J'évaluerais sous l'angle RGPD et sécurité le flux sortant vers Netdata Cloud : ce service tiers conservait noms et caractéristiques des serveurs et état des alertes ; les métriques y transitaient à chaque consultation.

La suite du fil rouge, en 2026 : la supervision du réseau avec Zabbix et Grafana en SNMP, puis un SOC Wazuh, pour passer de « voir l'état des serveurs » à « repérer une attaque ».
